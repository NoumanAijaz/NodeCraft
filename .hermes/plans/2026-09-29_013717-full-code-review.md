## Goal

Perform a complete, part-by-part code review of the NodeCraft repo (server + React
client), log every finding, fix the clear wins with verified commits, and deliver a
ranked findings report — done in context-sized "parts" so a 170k-context model never

## Current context / assumptions

- **What it is:** NodeCraft is a node-based diagram editor. Vite + React 19 + TypeScript
  client (`src/`), Zustand for state, `@xyflow/react` canvas. A separate Express 5 (ESM,
  `node:sqlite`) server under `server/` handles auth (JWT + bcrypt), per-user project
  storage (JSON files on disk), and version snapshots.
- **No unit-test harness exists.** `package.json` has no `test` script and no vitest/jest.
  Therefore this plan uses the project's *real* gates as the verification loop:
  `pnpm run lint` (oxlint) and `pnpm run build` (`tsc -b && vite build`), plus
  **manual HTTP checks** against a running server. Do **not** invent a TDD test suite.
  (If you find a cheap, high-value way to add a real harness, that's a 🔴 ASK item.)
- **Real gates (verified on this machine):** Node v26.7.0, pnpm 11.22.0. `pnpm run lint`
  currently **exits 0**. `pnpm run build` is the type-check + bundle gate.
- **Working tree is DIRTY and must be reviewed + committed as part of this work:**
  10 modified files + 1 untracked (`.env.example`). The uncommitted diff is a
  **security-hardening batch** (401 vs 403, bcrypt timing-equalizer, per-username rate
  limit key, global JSON error handler, `x-powered-by` disabled, version-dir cleanup on
  delete, NaN-timestamp sort guard, zoom-aware edge hit-testing, zero-size shape clamp,
  Escape-key handling). Part A–G must *verify this uncommitted work is correct and
  complete*, then commit it deliberately.
- **Untracked `.env.example`** is a documented, non-secret template (PORT, CLIENT_ORIGIN,
  `JWT_SECRET`, `NODE_ENV`). It should be committed. Verify it contains **no real secret
  values** before committing (it must be placeholders/comments only).
- **Severity scale used in the findings log:** `C` = critical (data breach / RCE /
  auth bypass), `H` = high (auth, IDOR, path traversal, injection), `M` = medium (logic,
  leak, edge case), `L` = low (style, DRY, perf nit).
- **Commit discipline:** batch related findings into one commit; never commit broken
  lint/build. Message format: `review(<area>): <imperative summary>`.

## Architecture / proposed approach

Review the codebase in **seven context-safe parts** (server → client → cross-cutting),
each small enough to fit comfortably in a 170k-context window. Every finding goes into a
single append-only log (`.hermes/review/findings.md`) so no part loses findings to
context eviction. Clear, safe fixes are applied immediately and verified against the real
gates (`lint` + `build` + targeted HTTP checks); anything that changes behavior the user
might care about, or that is risky to auto-fix, is logged and marked 🔴 ASK. The
deliverable is a clean lint/build, a set of small verified commits, and a ranked
findings report.

## How to work each part (the RED→GREEN loop, adapted to no test harness)

Repeat for **every** finding you decide to fix (do this inline, per finding or small
batch — not at the end):

1. **RED — reproduce / confirm the defect is real.** For server code, start a server and
   hit the endpoint with `curl` and show it misbehaving (see Part A for the exact
   commands). For client/logic defects, cite `file:line` and explain the failing path;
   if it affects rendering, run `pnpm run build` (must pass) and note the visual/logic
   symptom.
2. **GREEN — apply the minimal fix** at the exact `file:line`. Match existing style.
   No drive-by refactors.
3. **VERIFY** the gate actually passes (do not trust the claim):
   - `pnpm run lint` → expected: `Found 0 problems` (or pre-existing warnings only), exit 0.
   - `pnpm run build` → expected: tsc reports no errors and Vite prints a successful
     build with asset sizes; exit 0.
   - For behavior changes, the specific `curl` from step 1 now returns the expected
     status/body.
4. **COMMIT** the batch: `git add <specific files> && git commit -m "review(<area>): <summary>"`.
   Do not `git add -A`.

- **No test harness (biggest gap).** Fixes are verified by lint/build + manual `curl`/
  smoke tests, which is weaker than a regression suite. **🔴 ASK:** do you want a minimal
  `vitest` harness added for the highest-risk server logic (auth, ownership/IDOR, path

- **Dirty working tree.** The 10 modified files are an uncommitted security batch. My

- **Data safety.** Several findings touch project/version files on disk. Any fix that
  deletes or rewrites user files will be shown to you before it runs. **🔴 ASK** before any
  data-mutating fix.
- **Auth hardening changes (401 vs 403, timing-equalizer, per-username rate limit) change
  observable behavior.** If any downstream client depends on the old 403 or on
  IP-only rate limiting, this could surprise it. **🔴 ASK** if there are other clients
  against this API.
- **`localStorage` for the JWT** is the pragmatic choice here but is the weakest auth

- **Scope guard.** This is a *review + fix* pass, not a rewrite. I will not refactor

- **Open question:** is `server/reset-password.mjs` intended to ship (it's in the repo)?
